01

The finding that changes the architecture

GitHub Copilot reads .claude/skills/. Agent Skills went GA on Copilot on 2025-12-18 as an open standard explicitly interoperable with anthropics/skills. Copilot's project skill directories are .github/skills/, .claude/skills/, and .agents/skills/ — across VS Code agent mode, the Copilot CLI, the cloud agent, and code review.
So a single physical SKILL.md serves both hosts. No generator. No symlink. No rulesync. The dual-host problem that would have dominated this design mostly does not exist — at the skill layer.

What it gets right

  • Correct discipline. It refuses to assert unofficial advice: "When the spec or official docs do not state a recommendation, do not present it as a best practice." That is the right instinct and most prior art lacks it.
  • Right format. Anthropic-style SKILL.md with progressive-disclosure references/, which — as of Dec 2025 — is the format both hosts read.
  • Good routing. It points at canonical containers.dev URLs rather than paraphrasing them.

Where it fails

  • It is a router, not a rule set. Seven rules, zero execution, zero audit, zero generation.
  • The README overstates the skill. It advertises "use Features when possible", "non-root user", "prefer official Features/templates" — none of which appear in SKILL.md as rules.
  • It has already rotted. Its Zed claims contradict current Zed docs. Its CHANGELOG links a v0.1.0 tag that does not exist, so the README version badge is broken. Its MIT LICENSE has no copyright holder.
  • Real spec gaps: never mentions waitFor, secrets, lockfiles, feature dependency resolution, image-metadata merge rules, or updateRemoteUserUID.

04

The portable frontmatter intersection — try it

The one thing a shared SKILL.md genuinely cannot dodge: the two hosts accept different frontmatter keys, and a third consumer (claude.ai upload / the Skills API) is stricter than both. Toggle the targets you need and watch the legal key set shrink.


    

  

  

    Five keys are portable. We ship four — and that is a choice, not a constraint. allowed-tools is in the portable set. Its values are not: Claude writes Bash(node:*), Copilot's grammar is a different kind namespace (shell(...), write). A single string is wrong on one host either way, so the design omits the key and lets each host apply its own permission flow. Portability of a key does not imply portability of its value.
    
unverified metadata is in the agentskills.io portable six but is not in Copilot's own documented optional-key list. Gate A settles it; if Copilot balks, corpus_version moves into the body and the shipped set drops to three.

What four of six independently refused

      
Any generated prose projection of the rule corpus into the model's context. A RULES.md, or an applyTo-globbed instructions file listing every rule.

      
Two reasons, both fatal. It installs a second source of truth at the consumption boundary. And it hands the model a fluent answer key, so it can produce a confident-sounding audit without ever running the check.

    

  







  
06
The plan


  
Phase 0 — five gates that block everything A–C: 2–3 h · D: ~1 d · E: after the draft

  
Every candidate asserted A–D rather than checking them. Gate E came from the Codex review and is the one that tests the actual claim. Each gate, if it fails, invalidates a different piece — which is exactly why they go first.

  
A
Do the skill installers preserve subdirectories and the executable bit? npx skills add, gh skill add, copilot skill add. If any flattens the tree, every design with bin/ or references/ breaks on its own advertised install channel.

  
B
Does Copilot resolve skill-relative references/*.md from .claude/skills/? Documented for .github/skills/; unverified from the shared directory. Level-3 progressive disclosure — the whole reason depth is affordable — depends on it.

  
C
Can Copilot code review shell out? It is the highest-value surface for an auditor (findings land on the diff) and is plausibly non-executing. If it cannot, the executable-checker story dies exactly where determinism mattered.

  
D
What are the false-positive and recall rates on ~300 real public devcontainer.json files? Every quality gate proposed so far is self-referential: fixtures are built to trip the rule they test and pass by construction. Decides whether Phase 2 exists. Above ~10% FP on working configs, prose-with-citations wins. Budget half a day to a day — the hand-adjudication cannot be automated without defeating the point.

  
E
Does the skill actually get selected, and does it change the answer? Ten realistic tasks with expert-labelled correct answers, run on three surfaces with the skill installed and removed — 60 runs. Three numbers: firing rate, lift (correct-with minus correct-without), and harm (tasks made worse). This is the Phase 1 exit criterion, and no candidate architecture contained it.
  
lift ≥3/10, harm 0 ship · lift 1–2 the problem is selection, not rules — rewrite the description, don't add rules · lift 0 stop. Fall back to twelve facts in AGENTS.md and record that as the finding.

The twelve rules — the facts a model gets wrong unaided

  
Not thirty. Twelve. The corpus is the delta between what a frontier model already knows and what it confidently gets wrong — which shrinks as models improve, so the corpus should shrink too.

  


  
Phase 2 — conditional on Gate D only if clean

  

    

      
    
        
  • bin/dcaudit.mjs — zero-dependency Node, stdlib only, ~150 lines, bare node, no package.json, no build step.
    • 
        
  • The JSONC decision is forced before a line is written. devcontainer.json allows comments and trailing commas; JSON.parse does not; a regex stripper mangles // inside strings. Either shell out to devcontainer read-configuration, or write a real character-scanner — or abandon Phase 2 and contribute to decolint instead. This is where a home-grown checker quietly becomes a worse decolint.
    • 
        
  • A provenance header (tool_version + corpus_version + generated_on). It is not tamper-evident — it is self-reported, and anything can emit three plausible lines. What it buys honestly: when the checker did not run, the header is absent, so "the skill silently stopped firing and you got a confident wrong answer" becomes a visibly missing line.
    • 
        
  • Corpus moves to rules.json + rules.schema.json, with a bijection test against the checker.
    • 
      

    

    

      
    
        
  • Fixtures: fixtures/clean/ tripping nothing, fixtures/dirty/ tripping a known ID list.
    • 
        
  • SARIF to GitHub code scanning, Actions annotations as fallback. A finding on the diff line is a different product from a finding in a log nobody opens.
    • 
        
  • A recommended .claude/settings.json permissions snippet and the matching Copilot CLI --allow-tool line, so the checker is pre-approved instead of prompting.
    • 
      

    

  


  
Phase 3 — upstream, and run it early

  

    Send the github/awesome-copilot pull request first. That repo has zero devcontainer instruction, prompt, or chat-mode files today. One file, reviewed and maintained by someone else, reaches more users on day one than a standalone repo will in a year — with zero ongoing maintenance surface, zero portability lint, zero distribution question.
    
Then a PR to decolint for the 5–8 semantic rules it lacks (lifecycle placement against prebuild boundaries, waitFor enum legality, label-storability, ${devcontainerId} scoping, Codespaces divergence, userEnvProbe) — inheriting its --merge effective-config resolution instead of rebuilding it.

  


  
Phase 4 — the mechanism nobody else proposed

  

    
Quarterly, re-run the Gate E task set unaided — and suppress every rule the base model now gets right.

    
Every proposal on the table has machinery for adding rules, citing rules, and detecting stale citations. None has machinery for detecting a rule that has become unnecessary. The value of this corpus decays monotonically as models train on containers.dev; within a year the honest set may be five facts, not twelve. A freshness job detects a moved URL. Only this detects a rule that stopped earning its place.

    
Suppress — never delete. The first draft of this plan said delete; the Codex review was right that it is unsound. Passing an eval once is not evidence a model applies a fact reliably in a noisy repo, on every surface, at every version. A suppressed rule sets prompt_include: false: it leaves the prose the model reads but stays in the corpus, the checker, and any SARIF baseline. Suppression is reversible when a model regresses. Deletion is not.

  







  
07
The strongest case against building any of it

  

    

      
Do nothing

      
Revealed demand is near zero and it is measured, not inferred: afonsograca 1★ and abandoned at three months; decolint 1★; mmalyska 0★ and unlicensed; awesome-copilot has zero devcontainer files; anthropics/skills has none. The most-used devcontainer skill in the wild is a generator — people want a devcontainer created, not audited.

      
Every architecture here reasons "the prior art is thin, therefore build a better one." The alternative reading — the prior art is thin because the market is thin — was never entertained until the critic raised it.

    

    

      
The cheaper ladder nobody costed

      
Rung 0 — nothing. Accept the editor squiggles and the rebuild error.

      
Rung 1 — twelve facts in the AGENTS.md the team already has, plus one @AGENTS.md line in CLAUDE.md (Claude Code does not read AGENTS.md; Copilot does). Thirty minutes, reaches both hosts today, and a fact you did not write down cannot rot.

      
Rung 2 — the same twelve facts as one portable SKILL.md with a source URL and a date on each. This is Phase 1.

      
Rung 1 captures most of the value at roughly 2% of any proposal's cost — and no candidate costed it.

    

  


  
What every candidate missed

  
Lifecycle commands have an object form that runs in parallel base.json
postCreateCommand is "type": ["string","array","object"], and each object entry runs concurrently. Not one of four candidates mentions it — and it silently breaks every proposed "is this command expensive" heuristic, which all assume a single shell string.

  
userEnvProbe — the answer to the most common devcontainer question there is devContainerCommon
Enum none|loginShell|loginInteractiveShell|interactiveShell, default loginInteractiveShell. It is the mechanistic explanation for "why does my command work in the terminal but not in postCreateCommand", and it is one line of a rule. Zero coverage anywhere.

  
_REMOTE_USER, _CONTAINER_USER, _REMOTE_USER_HOME, _CONTAINER_USER_HOME features spec
Feature install scripts run as root; these four variables are the only sanctioned way to learn the eventual user. It is the #1 cause of root-owned files in a Feature. Three candidates ship a root-owned-files rule that this fact explains, and none names it.

  
devcontainer features resolve-dependencies — the official oracle, unused CLI
Three candidates hand-author prose rules about dependsOn vs installsAfter vs overrideFeatureInstallOrder — the hardest corner of the spec — and not one calls the maintained command that simply prints the resolved order.

  
customizations is an open namespace with no registry — so it is the legal home for config spec
Two candidates invented and then deferred an rc-file for per-repo rule suppression. The config file already has a spec-sanctioned address inside devcontainer.json. The same fact is also why an unknown-property check must never descend into customizations.*.

  
The Claude-Code-in-a-devcontainer cluster 3 footguns
--dangerously-skip-permissions is rejected as root, so remoteUser must be non-root. Auth persistence needs a volume at ~/.claude and CLAUDE_CONFIG_DIR set, because ~/.claude.json lives outside ~/.claude. The reference firewall needs NET_ADMIN + NET_RAW via runArgs. For a package built for Claude Code and Copilot users, one candidate covered one third of one of these.

  
Unserved jobs: Templates, compose, migration, prebuild economics, WSL2/arm64
Zero of four candidates mention devcontainer-template.json at all. Across ~20–30 proposed rules there is not one compose-specific semantic rule — so anyone with a database in their dev environment is unserved. Nobody offers migration ("bring our 2021 config to 2026") as a first-class job, nobody frames prebuild economics as the money question it is, and no corpus covers WSL2 filesystem placement or arm64/amd64 mismatch — a leading "won't build" cause.


  
What makes this obsolete

  

    
6–12 months — devcontainer validate ships upstream. The CLI shipped 0.86, 0.87 and 0.89 in 2026 alone; schema conformance is its most obvious missing subcommand. The week it lands, three candidates' flagship differentiator becomes a wrapper around one command.

    
3–9 months — decolint grows the eight semantic rules. Seven weeks old and moving. It already owns effective-config --merge resolution that nobody wants to rebuild.

    
12 months, certain — the model learns the rules. The whole thesis is "facts a model gets wrong unaided." That set shrinks monotonically. Phase 4 is the only defence anyone proposed.

    
Which is why Phase 3 comes early. An upstream PR keeps its value when the package does not.

  







  
08
Executing it in the next session

  

    
Gates A–C → 3 subagents
Fully parallel, no shared state, ~2–3 h. Each returns a structured verdict. Gate D is its own day-long task; Gate E runs after the draft skill exists and is the Phase 1 exit criterion.

    
Phase 1 → 4 subagents
One per artefact: SKILL.md body · rules.md (12 rules with citations) · spec-facts.md · README + pointer. Then one citation verifier that re-opens every URL and checks every quote before anything merges.

    
Codex as advisor
At each phase boundary, not in the loop. Time-boxed and non-blocking — and check for an empty payload before treating a non-zero exit as a review. Its first pass already changed nine things in this plan.

    The one non-negotiable review gate: no rule merges without a source URL, a verbatim quote under 300 characters, a verified_on date, and a SPEC or OPINION tag. That is the single discipline afonsograca got right and mmalyska got wrong — and it is what stops this from becoming another 1-star repo with a broken version badge.
